The whole specification as recipes

Every recipe re-expressed in 7 primitives — and the same 7 building the world from an empty game. Generated from tools/research/formulas/data.json.

The one finding

Creation and transformation are already the same format, because the specification has been quietly turning relations into things. deposit and adjacency are kinds. Once a relation is a thing, building the world is change and call with nothing that can refuse — the identical primitives that play the game, and nothing added for world-building at all.

The primitives

There are 7. change carries the guard, so it is the only line that can refuse on a count; set exists only to change a thing that already exists, since a positive change carries its traits.

Primitive What it does Example Why it earns a place
change Add a signed amount to a count, and fail if the result would go below zero change -3 metal in t one operation: creating is a positive amount and spending a negative one
require A read: at least n, and not consumed require 1 adjacency from -> $to the one guard that is not a cost - a read arc, used once
set Assign a trait on a thing that already exists set extractor.ready = no only for changing a thing, since a create carries its traits
attach On any line: what to do when the result would go below zero change -1 labor in t [hard] one question, and hard, soft, clamp and record are its four answers
each Bind a name over every member of a set, and repeat the lines below it once per member each t: {territory} the one construct that cannot be expanded when it is written - see *Repetition, or quantification*
some Offer the lines below it once per member of a set, for the player to take or leave some t: {territory control:yours} the other half of `each` - the same field, and it is what `owner` was
call Apply another recipe with arguments call found-colony(t) [soft] the hierarchy, and what keeps recipes short without adding expressiveness

The attach column

What happens when a line cannot do what it says. Five values, of which two are in use, one is the absence of a question, one is in the game without a name, and one is a candidate that depends on a decision about a different column.

Value What it means What to know Status
(blank) The count provably cannot go below zero, so no attachment is meaningful. Not a value so much as the absence of a question. Check 4 finds these mechanically: a create whose container has no capacity, a set on a thing that exists. IN USE - create citizen in t
hard The subtraction would go below zero, so the whole action fails and nothing happens. The right default for anything spent. A player is told why, and the state is untouched - so a failure costs nothing but the click. Subtraction as a partial function: undefined, and the caller fails. IN USE - every consume that pays a cost
soft The subtraction would go below zero, so skip this line and carry on. The action still succeeds. A capacity is a count of free space, so a container that will not take another is the same condition as any other underflow. One meaning, not two. IN USE - create garrison in t, and age
clamp Do as much as the state allows. Take 3 where there are 2, and take 2. This is monus - truncated subtraction, the operator that makes the natural numbers a commutative monoid: a - b is 0 when b exceeds a. The standard way to total a subtraction that is otherwise partial. CANDIDATE - and it is now a named operation rather than an invention
record Take what is there, write the shortfall where another recipe can read it, and carry on. `unpaid` is a trait - derived: its upkeep was not met - and `perish` fires on it. So a failed upkeep is neither hard nor soft. This is the value Sean's rule names: the population lost to starvation is an event, never a negative number. IN USE - upkeep, read by perish

Which lines can fail at all

change can, and it is the only line that refuses on a count — that is what fusing the guard into it means. A negative change fails when there is not enough; a positive one fails only where a capacity is declared, which is the same condition seen from the other end, because a capacity is a count of free space. require can, being a read that has to find something. call can, when something inside it fails hard. let can, when a path does not resolve — ark.location.below has no answer for an ark that is not in orbit, and hard is the only sane value there. set effectively cannot, which is why no set in this report carries an attachment.

What is sugar

Removable with linear growth, so by the test each is readability rather than expressiveness — which means they can be added freely.

Written as Means Cost of removing it
create n k change +n k linear - a name for a positive change
consume n k change -n k linear - a name for a negative change
let x = path substitute the path at each use linear - readability only
destroy k change -1 k, where k is an identified thing DELETED as a primitive - it was a change with the count left implicit
threshold(k, at least n) then n destroys change -n k DELETED as two lines - it is one, and 15 of the 16 guards were this
create k then set k.trait change +1 k[trait:value] DELETED - composition is not sequential, so a set on a thing this recipe creates has no referent. Four world-building recipes were this, and 13 lines became 4
limit n k DELETED - a container's capacity, declared once in Capacities both uses were restatements
a recipe's prose <em>selection</em> each x: {description} DELETED as prose - six world recipes quantified in a field the language could not see
the <code>Owner</code> column each (the world's) or some (the player's) DELETED - the distinction is which quantifier, and the specification already says so: the player's are offered, the world's are not

The last column: every row as one string

The last column of every recipe table restates that row — op, target, amount, attach and the note — as a single string in the notation spec/console.md gives for a command and for a description of state: {name field:value ...}, where a value is a word, a number or another command, a field referring to a thing is named for that thing's kind, and # begins a comment. All 77 lines are encoded, none by hand.

Two of a territory's four traits have no value anywhere

biome and nature are stored traits of every territory, and no document gives either one a value for any of the twelve. Territory resources has four columns and none of them is a biome; the Biomes table describes what each biome is like and says force of nature is the one column that binds, which binds a territory's nature to a biome it has not been given. The code assigns them — biomes_of, which R-4 vetted — so this is where a thing lives in two authorities at once, and only one of them is a document.

This report asserted otherwise until today. Its world-building data said make-territory(1, grassland, 1), which named a biome for territory 1 and a nature for it, and nothing states either. Removed rather than corrected, because there is no correct value to put there. It was found by trying to draw the table above and having two columns come up empty — which is the argument for drawing it.

metal.density or density.metal: neither

The question only exists because the resource has been moved into the name. density is a variable and metal is a value of a different variable, resource — so once resource is a column there is nothing left to order, and the row above reads {deposit territory:1 resource:metal total-capacity:.. density:..}.

The specification already rules on this, and not by analogy. Nothing in the state is special to a kind. Adding a kind adds no field and no case, and whatever reads the state reads it the same way whatever kind it holds. A territory carrying metal.density, food.density and energy.density gains a field per resource, which is exactly what that forbids. The long form gains a row per resource instead, and rows are free.

The instinct behind the dots is right about presentation and wrong about statement. The release's Territory resources is wide on purpose — one row per territory, a resource per column, 3 x 4 packing two variables into one cell — and it is far easier to read than 13 rows would be. CLAUDE.md already separates these: a table of game data in markdown is a rendering and never a source. Both forms exist above, and the wide one was generated from the long one rather than the other way round.

Repetition, or quantification

Sean, 2026-09-09: should we have a construct for repetition? It is an extra construct but has the potential to lower the number of instructions needed. Then, a minute later: I suppose repetition and quantity are similar concepts.

They are the same concept, and the specification already says exactly when. change +2 citizen in t is the creation of a citizen repeated twice — the amount column is a repetition count written as a number. So there is no question of adding repetition; it is there, and it is called a quantity.

The line between them is whether the repeated things are distinguishable

spec/console.md: what a thing contains is a map from a description to a quantity, and each distinct description is its own entry. So a quantity is always per description. Two citizens made in the same territory share a description, so they are one entry of two. Twelve territories have different ids, so they are twelve descriptions and no number can merge them.

The rule is already stated from the other side as well: there is never a quantity of a thing with an id, and a thing carrying one has a description no other thing shares, so its quantity is always one. change +12 territory is therefore not merely awkward, it is forbidden — and that is the whole reason make-territory has to be called twelve times rather than once with an amount.

So the missing construct is not repetition. It is what you need when repetition cannot collapse into a quantity, which is quantification: one firing per member of a set, with something bound differently each time.

What it isWhere it is used Is it expressible?
Repetition the same thing, n times 8 changes whose amount is more than one Yes, twice over. The amount column does it for a change, and spec/console.md gives a command a repeat, which is how many times it fires. A third way would buy nothing.

Added 2026-09-09, and what it cost

each <name>: <set> binds a name over every member of a set and scopes the lines below it, up to the next each or the end of the recipe. One rule covers both shapes: a world recipe has one at the top scoping its whole body, and make-world has four, each scoping the call beneath it.

It cost ten lines and a sixth primitive, and bought the thing the constraint asks for rather than conciseness: the six world recipes and the four world-building calls now say what they do in the language, where before they said it in a field and a comment that nothing could run. 20 quantifiers, 17 of them over a description of the state - the rest range over a data table or over the planet's geometry, which the notation has no form for and which the assumption list records.

It changes nothing about the checks, and that is on purpose. An each has no effect of its own: it says how many transitions a recipe is a source of, and the lines below it are the transition. So checks 1 and 2 weigh the body, exactly as spec/invariants.md describes - a rule is a source of transitions, not a kind of one. Weighing the whole would make a recipe's net effect depend on the size of the planet, which is not a fixed vector at all.

It is not sugar, and the reason is xE

The test this report has used since X-11 is Felleisen's: a construct is eliminable if a local expansion removes it without restructuring anything. Quantification over twelve territories expands to twelve lines — linear, and by that test sugar.

Except that twelve is not a constant. spec/console.md has create planet <size> and spec/planet.md has five planet sizes, so the number of territories is a parameter and the number of shared edges is whatever the geometry gives — which is why that row's multiplicity is written xE and not a number. You cannot expand what you cannot count when you write it. So quantification is not removable by a local expansion, which is precisely what it means for a construct to add expressive power rather than convenience.

And it is already half-built, in two places

spec/invariants.md: a rule is a source of transitions, not a kind of one. A rule that is a source of many is a schema, and turning it into its transitions is quantification — so the specification has already committed to this, and the word for it is grounding.

check.py does it today. work names the family resource and the checker expands it into work[food], work[metal] and work[energy], which is X-17. That is a quantifier over a family, already implemented, and the same operation an interface performs to build a menu. What is missing is not the machinery but a way to write it in a line.

The caveat is the same one X-9 gave call. A quantifier ranging over a set the recipe does not change is finite and free. One ranging over something the recipe itself creates is a loop, and that is where the analysis stops terminating. Each territory is safe; each thing this makes is not.

Defining a kind, then using it

Sean, 2026-09-09: can we define what an ark is first, then define recipes that define what an ark does? Is that kind of thing possible with our current model?

The specification already commits to it. spec/invariants.md: the definitions are part of the game state, and defining one is a transition like any other, so a game's history is a complete account of it, including what its rules were. And a definition arrives in one transition; there is no state in which a kind or a recipe is half defined - which is exactly what a positive change carrying its traits now does.

Neither kind nor recipe is one of the sixteen kinds, so a definition has nowhere in the state to be - and everything but the game has to be somewhere. The fix is small and mechanical: two kinds, and two declarations saying the game may hold them. Half the step is taken already, since call writes recipe:found-colony as though a recipe were a thing with a name, six times.

The ordering is not a difficulty. Defining the ark and defining what it does are two transitions, and a recipe that needs a kind to exist first can say so with the primitive that survived for exactly this shape: require 1 {kind name:ark}. A read arc makes the dependency explicit and checkable rather than a matter of writing them in the right order.

The limiting factor is analysis, and it is narrower than this report first said

Every check on this page assumes a fixed set of transitions. Check 2 builds a matrix of them; check 1 weighs each one; check 6 reads them all. So the question is not whether definitions happen, but whether the set they produce can be known.

Corrected the same day. This section first said the design-time distinction was what kept the checks meaningful. That is not it. Manual definition costs nothing at all — these are edit-time checks over a fixed rule set, so writing a new recipe means re-running them, which is what an editor does anyway. A person adding a recipe during play is still a person. The line is not the phase, and it is not who is at the keyboard.

The line is whether the set of recipes that could ever exist is finite and knowable in advance. A recipe that picks a definition from a fixed catalogue is a reconfigurable net, and boundedness stays decidable for that class. A recipe that composes an arbitrary new recipe out of the state is a net rewriting system, which is Turing powerful, and the decidable properties of Petri nets are lost with it. So automatic definition is allowed too, on that condition — which is a much weaker restriction than a phase.

Time flowing one direction buys something real, and it is not what saves you

It makes the per-transition checks incremental. Checks 1 and 6 are properties of a single recipe read on its own: does this recipe conserve metal, does this line put its thing somewhere declared. A recipe that passes them passes them forever, and nothing later can un-pass it — so with time going one way you check only what is new.

Check 2 is not like that, and here is a recipe that proves it. Adding change +1 deposit in t - a deposit out of nothing:

as it stands                 check1 green (12)   check6 green   check2 undeclared gain: none
add: a deposit from nothing  check1 green (13)   check6 green   check2 undeclared gain: deposit +1

It conserves metal, because a deposit has no Binding, and it puts the deposit somewhere a territory declares. Both per-transition checks stay green and the whole-net one goes red. Boundedness is a property of the matrix rather than of any row in it, so one new transition can create a loop among transitions that were all fine before.

So the working rule is cheap and precise: on defining a recipe, check the new one against 1 and 6, and re-run 2 over everything. Monotone time is exactly what makes the first half incremental, and it does nothing for the second.

Detecting a glitch, without a cap

Unbounded capacity does not cost you detection

Boundedness for one starting state is EXPSPACE-complete. Boundedness for every starting state is polynomial — a linear program over the incidence matrix. The second is the one an editor needs, because an author is editing recipes and not a saved game. A net is not structurally bounded exactly when there is a non-negative firing vector x, not all zero, with C·x ≥ 0: a set of recipes that, fired in some ratio, ends with more than it began. The vector is the error message — it names which recipes and how many of each.

All of it needs the plain fragment. A zero test on an unbounded quantity makes the language Turing-complete and every line of this section false.
