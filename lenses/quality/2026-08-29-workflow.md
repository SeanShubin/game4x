# A recommended workflow

**Derived.** Written by the quality instance on 2026-08-29. **Input to a decision, not an
observation about the tree.** The decision is Sean's and belongs in [`CLAUDE.md`](../../CLAUDE.md),
which is the documentation lane's file. Companion to [notes on lenses](2026-08-29-lenses.md).

[Quality](README.md) · [CLAUDE.md](../../CLAUDE.md) · [The proposal queue](../../docs/notes/proposals.md)

Sean named six constraints: he must review the specification himself; the specification must give
code enough to execute; code sometimes needs an answer from him; research often is not ready for
either; each instance should stay focused; and quality finds failings in both.

Those are six constraints on **one** mechanism, not six mechanisms. This repository already has the
mechanism and uses it for exactly one of the six.

---

## What is actually missing

Seven things move between the perspectives. Six have a named channel:

| What moves                      | From          | To          | Channel today            | State                         |
| ------------------------------- | ------------- | ----------- | ------------------------ | ----------------------------- |
| A decision to make              | lens, or Sean | Sean → spec | `proposals.md`, numbered | Works. The model for the rest |
| Intent said but not written     | Sean          | spec        | `spec-backlog.md`        | Works                         |
| What to build now               | spec          | code        | `releases/`              | Works                         |
| Research not ready for anything | lens          | nobody yet  | the lens's own directory | Works - and is the point      |
| A defect in code                | lens          | code        | a report, pulled         | Works; needs an addressee     |
| A defect in the specification   | lens          | Sean → spec | a report → a proposal    | Patched last week, by hand    |
| **A question that blocks code** | **code**      | **Sean**    | **conversation**         | **No channel at all**         |

The last row is Sean's third constraint and it has nowhere to live. Today a blocked question is
asked in a reply, which is the failure mode `CLAUDE.md` names by name: *it reads like diligence and
behaves like forgetting.*

Worth noting what makes this easy to miss: **every `spec/` file already has an `## Open questions`
heading, and all twelve are empty.** The slot for "what still needs deciding" exists, is unused, and
sits in a directory only Sean writes - so neither code nor a lens can put anything in it even when
that is exactly where the question belongs.

## The one mechanism

`proposals.md` works. It is numbered, dated, says where the content is destined, separates accepted
from rejected, records the reason for a rejection, and carries a promise about being empty. Nothing
else in the repository has all five properties, and nothing else has survived contact as well.

**Generalise it rather than inventing per-lens formats.** Every perspective keeps an **outbox** in
its own directory - the one place it may write - and every item in an outbox carries four fields:

| Field        | Why                                                                                       |
| ------------ | ----------------------------------------------------------------------------------------- |
| **id**       | Stable, so a commit can cite it and a later report can say what happened to it            |
| **to**       | `sean`, `spec`, `code`, or a named lens - or **absent**, meaning *not ready, do not read* |
| **status**   | `open`, `answered`, `acted`, `rejected`, `withdrawn`                                      |
| **one line** | What it is, so a reader can triage without opening the report                             |

`to` is the field that does the work, and it is the one nothing has today. It converts every
instance's reading list from *a directory sweep* into *a query* - which is precisely Sean's fifth
constraint, that each instance stay focused without being distracted.

### What each perspective then reads

| Perspective | Inbox                                                                | Never has to read       |
| ----------- | -------------------------------------------------------------------- | ----------------------- |
| **Sean**    | Everything `to: sean` - proposals awaiting review, blocked questions | Any lens's raw research |
| **Spec**    | `to: spec`, plus `spec-backlog.md`                                   | Reports, code reviews   |
| **Code**    | `to: code`, plus `releases/`                                         | The proposal queue      |
| **A lens**  | Everything. That is what a lens is for                               | -                       |

And the absent-`to` case is the answer to Sean's fourth constraint. **Research that is not ready is
research addressed to nobody.** It lives in the lens's directory, costs no one any attention, and
becomes visible the moment the lens addresses it. Nothing has to be held back by discipline; it is
held back by not having a reader yet.

## The cycle

1. **Sean says something.** The spec lane records it in `spec-backlog.md`. Only the writing counts.
2. **A lens explores.** It writes in its own directory, addressed to nobody. This is where research
   sits for as long as it needs to.
3. **A lens is ready.** It addresses a finding: `to: spec` if it needs a decision, `to: code` if it
   is a defect in the build.
4. **The spec lane turns `to: spec` items into numbered proposals**, naming the destination file and
   section. It does not decide anything.
5. **Sean reviews the queue.** He edits proposal text in place until satisfied, then says
   *promote P-n*. This is the one step that cannot be delegated and should not be diluted, which is
   why everything above exists to keep the queue small enough to read.
6. **The spec lane promotes verbatim and asserts it landed.** A promotion that makes something else
   stale files the cleanup immediately.
7. **The spec lane updates `releases/`** to say what is being built now. A release never invents a
   rule.
8. **The code lane builds** from `releases/` and `spec/`.
9. **Code hits a gap** - and does *not* stop. It does everything not depending on the answer, files
   a question `to: sean` stating the assumption it proceeded under, and keeps going. Sean answers
   when he is next in the loop; if the answer is a new idea, it enters at step 4 like any other.
10. **A lens reviews the result**, and it returns to step 3.

Step 9 is the part I would write down most carefully, because "code sometimes needs answers from me"
turns into "the session stalls until Sean is free" unless the rule says otherwise. **A blocked
question is filed and worked around, never waited on.** The assumption is stated so that if the
answer differs, what has to be redone is known rather than discovered.

## The guarantee that makes it worth the ceremony

`CLAUDE.md` currently promises: *if the queue is empty, Sean can take it that nothing known is
inconsistent.* That promise is about `proposals.md` alone, and it broke last week - P-123's
contradiction sat in `quality/` for a day while the queue was empty and the promise was false the
whole time.

The generalisation is the one thing worth building:

> **If nothing anywhere is open and addressed, nothing known is outstanding.**

That covers proposals, blocked questions, and lens findings in one sentence, and it is the reason
the four fields need to be machine-readable rather than prose. With one lens, a person can check it.
With five, only a program can - and every hand-maintained index in this repository has rotted while
every generated or tested one has held. `tools/pad-tables` is precedent for a documentation tool
outside the workspace; this would be its sibling.

## The gap nobody is assigned to

Sean's second constraint - **the specification must give code enough to execute** - has no owner.

- The spec lane does not read code, so it cannot tell what was insufficient.
- The code lane reads the spec as instructions, so a gap does not look like a gap. It looks like
  something to decide, and the honest response to an under-specified rule is to invent one, which is
  how a rule the specification does not have gets implemented.
- Sean would have to hold both in his head at once, which is the thing the split exists to avoid.

It has been done once, by hand: `docs/notes/first-release-readiness.md`, *"What was missing before
the coding instance could build it"*, now marked superseded. It worked, and it was a one-off.

That is a lens, and on the evidence it is the one to add before any other: **read a release as if
about to build it, and file every question that would have to be answered first.** Its findings go
`to: spec`, which is exactly the `## Open questions` sections that are sitting empty in all twelve
spec files.

It also passes the test from [the lenses note](2026-08-29-lenses.md#7) cleanly - neither producer
would find these, for the two structural reasons above - which is more than a third of what this
lens has filed can claim.

## What I would not do

- **Do not give each lens its own report format.** Four fields, one shape, or the index cannot be
  generated and the guarantee goes back to being a habit.
- **Do not let a lens write into a producer's directory.** A lens that can edit `crates/` is a
  second author of the code with none of the responsibility, and its findings stop being
  independent evidence.
- **Do not route unaddressed research to Sean.** The holding pen only works if nothing looks at it.
- **Do not add the second lens before the index generator exists.** Every mechanism here that works
  was built before the thing it guards got large; the two retrofitted - the proposal queue and the
  quotation guard - each lost material first.

---

## Smallest version that would work

If the above is more ceremony than the project wants right now, the load-bearing parts are three:

1. **A place for a blocked question**, addressed to Sean, that is not a reply. Nothing else on this
   page is missing outright.
2. **An addressee on every finding**, so an instance reads a query rather than a directory.
3. **One command that answers "what is open and addressed to whom"**, so the guarantee is checkable.

The rest is naming and ordering, and can follow.
