Every reference is to a single opaque integer id - Sean, 2026-09-15: *I want the truth of the
data model to be fully normalized, which I believe means always referencing by ids, and a single
id at that.*

Sixteen relations are keyed by such an id and one is not. residency carries a quantity
and is keyed by its description, (what, where) - Sean, 2026-09-15: *it would make no sense to
have both an id and a quantity in the same logical model.* Nothing references a residency,
which is what lets it do without one.

The ids mean nothing and are not meant to be read. Making them legible is the user-facing
style's job, not this one's. What is legible here is the name column, which is decoration -
with two exceptions worth knowing: a row names its relation by relation.name, and a row's
values are keyed by column.name, so those two decorations are what the notation is written in.

# How many times a thing may still act

Sean, 2026-09-17, on an extractor that can be worked as often as there is labor for it:
*rediness is going to end up being a number of times we can do something rather than whether we
have done something.* So it is a quantity, and a quantity is a relation's.

An allowance is its own counted relation rather than a column on the thing. A column would
have meant going from working:3 to working:2, which is arithmetic on a named column and
something the engine cannot do; a quantity is arithmetic it already does, and running out is the
refusal it already gives. What that gives up is which extractor was worked - and two
extractors with one work each cannot be told from two extractors sharing two works by anything
the game can ask, because extractors are fungible.

One relation per kind of readiness, named for the activity, which is what spec/data/traits.4x
does with working, moving, laboring and bearing. Each is a column of the thing that has
it, so a readiness cannot outnumber the things holding it without anything saying so.

# What a trait is, and which kinds carry one

A trait is an allowance a kind carries, and it is the column that holds how many are left.
moving is one and working is another; a scout has a moving and an extractor has a
working, and refresh is one rule over both because the trait is an argument rather than
part of the rule's name.

Sean, 2026-09-18: *I don't like that I have a separate refresh command for each resource, I
feel like this should be parameterized somehow.* And on what the parameterisation has to reach:
*I should be able to declare separate things with separate commands, as well as explicitly
declare group commands. So i can refresh a scout, refresh a transport, refresh all movable,
refresh all workable, and their intersections.*

carries is checked both ways, which is what stops it drifting from the columns it
describes: a kind that carries a trait declares a column of that name, and a column named for a
trait is carried by the relation that declares it. Neither half is derivable from the other -
the first would let a column go undeclared, the second would let a carries row name nothing -
so the check is a pair and src/schema.rs states it as one.

A family carries what its members carry. unit declares moving because scout and
transport do, so {refresh what:unit trait:moving} is the group command and
{refresh what:scout trait:moving} is the separate one. That is Sean's their intersections
with no third mechanism: the pair of arguments is the intersection.

# What a composite is, and why the tree is the point

A rule is a leaf or a composite, and a composite names rules in order. `{part id:1
of:end-turn is:refresh seq:1} says ending a turn does a refresh first; {argument id:1 part:1
input:what value:unit}` says which refresh.

It is the clause layer one level up, and deliberately the same shape. A clause has an id and
{binding ...} rows name it; a part has an id and {argument ...} rows name it. Nothing here
is a new idea about how a rule is described - it is the existing idea applied to rules rather
than to rows.

Sean, 2026-09-18, on what the structure has to be: *Whatever it turns out to mean, it must be
able to organize the entirety of game rules is some type of acyclic graph or tree. Otherwise it
will be impossible for a human player to understand how to play the game.* So src/schema.rs
refuses a cycle and refuses a rule with two parents, and examples/tree.rs prints the whole of
it on one screen.

A rule with one parent may still be named twice by it. end-turn refreshes twice, once per
trait, and those are two steps of one order rather than two parents - which is what a person
reading the tree sees and what the check counts.

The roots are the player's menu. A rule that is somebody's part is fired by that somebody; a
rule that is nobody's part is offered. So nothing declares an owner: spec/data/block.4x says
owner:world and here the tree says it, which is one fact in one place rather than two that can
disagree.

Sean, 2026-09-18, on why a part is still a command in its own right: *Why can't refresh be
both a player command and part of the turn. It seems it will make it easier to read tests across
multiple turns if i see an end turn command, and it will be easier to test the end turn command
itself if i can test its parts.* Fired by name and offered to a player are two questions, and
this lane had collapsed them into one.


# A bin, and how many of each a place has room for

A bin is a kind like any other - {bin where:territory-1 what:metal} -> 4 is four metal bins
standing in territory-1, keyed by the pair the way an extractor is.

It is called a bin and not a store, because store is the engine's word. src/store.rs is
where rows are kept and five of the eight modules say store in a line that runs, so a game
noun of that name cannot satisfy tests/isolation.rs - *no relation or rule the data names
appears in code that runs*. The check found it; the name was not chosen for taste.

spec/logistics.md draws the same line and drew it first: *A bin is a thing. What holds a
kind is a store for that kind, and a thing with two bins holds two stores.* The thing is the
bin; what it is for a resource is the store. Sean asked for storage and this is the thing half
of it.

How many a thing has room for is {capacity ...}, which is a table and not a number.

Sean, 2026-09-18: *a territory has many types of capacities: one for bins, one for berth, one
for extractors. A bin can have many types of capacities: one for metal, one for food, one for
energy. A metal transport has 2 types of capacities: one for metal, one energy (which it uses as
fuel). If we omit a capacity, we can default that to mean it may carry none of that thing.*

`text
{capacity of:territory for:bin      what:resource per:territory} -> 4
{capacity of:bin       for:resource what:resource per:territory} -> 10
`

One trait column, and it restricts whichever side declares one. A territory has no what,
so the first row is about every territory; a bin has one, so it is about bins carrying that
resource. Two columns - one per side - was the first draft and it does not work: of:territory
has nothing to qualify, every column of a row must be present, and there is no way to write *not
applicable*.

A family named where a member is expected means each member, which is the rule
{refresh what:unit trait:moving} already runs on. Named twice in one row it means the same
member, so for:resource what:resource is a bin holding what it carries and not what it does
not. That sentence is the whole of the templating, and it needs no notation: src/notation.rs
still has no types and every value is still a word.

Sean, 2026-09-18, on why this is the shape to take: *so it is macro substitution, not
computation, yes, that indicates to me we are on the right track.* Expansion is bounded by the
family's size and cannot recurse, so what every check sees is the plain rows it always saw.

per is declared and not guessed, for the reason already written on {supply ... per:...}:
a container may be the place or be in it, and working out which relation every side has in
common is a guess where this is a fact.

Omitting a capacity already meant none. nothing_crowds_a_place says so in a comment - *a
kind named by neither is not in the arithmetic at all* - so the default is being written down
rather than added.

Sean, 2026-09-17: *Each territory will have a limit of how many storage structures of each
type it can hold.* This needed no new mechanism, and backlog.md said it would - it said the
cap had to be per description, not per relation, and that the weighted pool could not say it
because a pool is named per kind. Both true, and both about the pool. The limit was already
the right instrument and nobody had looked at it.

spec/logistics.md had the shape too: *What a thing may contain is a maximum per kind, per
family of kinds, or per kind carrying a particular value of a trait*. A bin carrying
what:metal is the third case.

A deviation worth seeing rather than settling. The same document says a place *declares none
of its own* capacity - it is the sum of what stands there. Here a territory does declare it, as
it already does for berths with {provides kind:territory what:berth} -> 6. The number has to
be visible in the test, which is Sean's rule and decides it for now: *I need see what the
actual numbers are, not some hidden default.*

# What may lie loose, and what may not

A resource over its capacity is in disorder; a structure over its capacity cannot exist.
Sean, 2026-09-19, on why one word has two behaviours: *structures behave differently from
resources in this regard. This is because structures are intentionally built for the purpose of
having that structure there, while resources are mined to be spent or stored.*

So a capacity is a maximum unless the thing it holds is loose. {loose kind:resource} names
the kinds that may exceed one, and there is nothing else it does: the check stops refusing, and
discard-disorder takes the excess at the turn's end.

Over capacity is still usable, which is the point. Sean: *i am going to have mechanics that
allow for stuff over capacity to be used in other recipies to avoid the waste.*
spec/resources.md had already said it: *Matter that is out of its source may be spent, whether
it is in disorder or in order.*

A family names its members, so one row covers every resource. It is not {state ...} and so
is not reified - a structural fact belongs beside {supply ...} and {stands-in ...} rather than
in every test's given.

What is lost is lost, and does not go anywhere. spec/resources.md says disorder *returns to
its source; Sean, 2026-09-19: This was a thematic statement rather than a mechanical one, I am
not sure our thin-engine needs that theme yet.* There are no sources here, so nothing has
anywhere to return to, and the theme is noted rather than built.

{loose kind:stock}

Labour is loose and nothing holds it, which together are the whole of unspent labour is lost.
Sean, 2026-09-20: unspent labor does not survive the turn and *excess labor to be removed the
same as discard-disorder.* No capacity row says nothing holds it; the absence of one does,
because a loose kind nothing gives room for has no room.

{repeats rule:R} is how a varying amount is said without arithmetic. spec/invariants.md:
*where a rule would need a quantity that varies, it is written as a smaller rule that fires as
many times as it can*, and the quantity is then how often it fired. Feeding a population is that
shape - as many citizens eat as there is food for, and nothing computes a minimum.

It draws from the world as it was when it began. What a firing makes cannot be spent by its
own later firings, so a rule that produces what it consumes cannot run away. Sean, 2026-09-19, on
the framing that gives it: *I am thinking that repeat should always have consume-once rather than
consume semantics.*

That is the termination proof: the pool it draws from is finite and only ever shrinks, so the
repetition stops without anything counting the turns. A rule that removes nothing has no such
pool and is refused - Malformed::NeverStops.

{scope rule:R input:I} says an input is filled by the engine, once per row of whatever it
is typed as - not by a command and not by an argument. A world-owned rule has no caller to
supply a place, and upkeep has to take a citizen and a food from the same territory, which
is a join every other rule makes through an argument.

On the rule and not on the part, so firing it by hand and firing it from the turn do the same
thing. Sean, 2026-09-19: *there are some things that happen in sequence, and others that can be
declared once and applied separately.* A scope is the second kind: it is true of the rule always.

So it is scoped per rule rather than per composite, which Sean's sketch put it on. The two
give the same answer here because these rules are place-local - all of upkeep everywhere then
all of perish everywhere is the same world as both in one territory then both in the next - and
the per-rule form needs no way for a part to be handed its parent's argument.

A scoped rule is therefore a part and never a root. The engine fills the input, so there is
nothing for a player to choose, and offered skips anything a part names.

# A line that takes what room there is

Sean, 2026-09-20, on an ark that lands where there is nothing to mine: *it is legal to deploy
an ark anywhere, individual rules may fail but the deployment succeeds. Consequences of legal
moves may be disastrous, but that is player choice.*

Every other role refuses the world it would leave, which is the right default and the wrong
answer here: a deployment that cannot place a food extractor would place nothing at all, and the
ark would be spent on nothing or not spent at all. {soft clause:C} says that one line takes

It reads the same arithmetic the world check reads, so what a soft line fits and what the
world would refuse cannot disagree.

says how much room there is and there is no room* are different worlds - which is why two
citizens always land and two extractors may not.


# A citizen, and the hunger a turn gives it

A citizen is not one person. spec/population.md: *It is the smallest group that can sustain
reproduction.* A count of them is a density across a territory, the same way a deposit is.

hungry is an obligation where moving and working are capacities. The machinery is the
same - one per turn, restored by the turn, spent by acting - and the difference is what unspent
means: a scout that did not move is fine, and a citizen that did not eat is dead.

That consequence lives in perish, a named step of the turn, rather than in the trait. Sean,
2026-09-19: *Hungry seems like not so much a capacity as it does a need, it seems the difference
is relevant and why it doesn't read as well as bearing.*

It was hunger for a day, and a noun was the wrong part of speech. The rule that chose it
was sound - a capacity is a gerund, moving and working and bearing, and an obligation is
not one - but a noun takes an amount. hunger:1 reads as how much a citizen eats, which is
the one thing it does not mean: every citizen eats exactly one food and the trait is one bit.

An adjective cannot be misread that way. You can have two hunger; you cannot be two hungry.
The evidence is as good as naming evidence gets - Sean read it back as *so hunger is how much
a citizen eats?* on 2026-09-20, having been handed the model the day before. A name that misleads
the person it was explained to is a name that misleads.

The distinction the noun was for survives, because an adjective among gerunds is still a
visibly different part of speech. What it costs is the turn: `refresh what:citizen
trait:hungry` reads less well than restore hunger - one use against the two clauses that match
on it, which is why it was the trade to take.

{state ...} says a citizen is something a world holds, which two things read: templating,
so that a row naming a family becomes one per member, and the test harness, which refuses a
given stating anything that is not a world. The second is what caught its absence - this
lane left the row out on the strength of the first reader alone.

bearing is a capacity where hungry is an obligation, and the grammar says which: a gerund
for something a thing may do, a noun or an adjective for something it owes. Sean, 2026-09-19:
Bearing is their capacity to reproduce, that makes sense to me.

It is what stops one citizen breeding with the whole surplus, exactly as hungry stops one
eating all the food. breed consumes the parent and returns it as one of two, with its bearing
spent - so no citizen breeds twice in a turn, and at most doubling falls out of the rule rather
than being stated anywhere.

That is what replaces borrow and the mainline's fertility token. Sean, 2026-09-19,
choosing: *clarity is more important than conciseness, so yes, lets not have borrow, and lean on
traits.* A borrowed citizen could be borrowed again; a consumed one that comes back spent cannot.

A citizen now has two traits, so a place can hold two citizen rows, and a clause that matches
citizens without naming both is ambiguous. upkeep and perish name only hungry and are
safe because bearing is uniform when they run - the turn restores it last, so every citizen
enters a turn fertile and the split exists only between breed and the refreshes. If that ever
stops being true the engine refuses rather than guessing, which is Refused::NotOneToTake doing
the job it was built for.

laboring is a citizen's capacity to work, and it is a gerund like the rest. Sean,
2026-09-20: citizen produces a labor that work then spends. spec/data/traits.4x already names
it beside working, moving and bearing, and schema.4x has quoted that list since the
allowances were built - so this is the fourth use of a mechanism rather than a new one.

It closes the loop. labor was consumed by three rules and produced by none: every test that
spent one stated it in a given, so a population could grow and starve but nothing it did made
the food it lived on. A citizen makes one labour a turn, and work spends it on an extractor.
